## Software
*Will be an STM32CubeMX/STM32CubeIDE project, not initialized yet*

### Source organization

The organizational idea is to separate the CubeMX-generated STM32 code from the project-specific application code:

```text
software/A4-Flight-Computer/
├── Core/                         # CubeMX-generated startup and HAL integration
│   ├── Inc/
│   └── Src/
├── App/                          # User-owned flight-computer application
|   ├── Inc/                      # Shared application headers such as config options
|   ├── Src/                      # General application sources such as initialization
│   ├── Services/                 # Services, state machines, etc. shared between tasks
│   ├── Tasks/                    # FreeRTOS task implementations
│   └── Interrupts/               # GPIO/timer/CAN interrupt handlers
├── Drivers/
│   ├── BSP/A4FlightComputer/     # Board-specific hardware abstraction
│   ├── CMSIS/
│   └── STM32H5xx_HAL_Driver/
└── Tests/
    ├── Unit/                     # Google Test unit tests
    └── Mocks/                    # Mock functions for use in unit tests
```

`Core/` should remain mostly as generated by CubeMX. Project-specific application code should be placed in `App/`, hardware interfaces specific to the A4 Flight Computer board
(i.e. accelerometer interface) should be placed in `Drivers/BSP/`, and Google Test cases and mocks should be placed in `Tests/Unit/` and `Tests/Mocks/`.

Handlers in `App/Interrupts/` shall be ISR-safe and perform minimal processing except setting/clearing flags and queuing data to be processed by Tasks. Hardware-independent logic
belongs in `App/Services/` and should not depend directly on STM32 HAL or FreeRTOS.

Unit tests are built on the host with Google Test. Application services
should be testable without STM32 hardware, HAL initialization, or starting the
FreeRTOS scheduler. Use interfaces and fakes for hardware-dependent behavior.
